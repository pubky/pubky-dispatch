# Signer host guide

For the developers of a host app, for example a wallet app acting as signer, that embeds the `pubky-switch-signer` crate. It lists every case the signer can put in front of the host, how the host learns of it, what the user needs to know and which decisions require confirmation. Section 3 gives a checklist for integrating these flows. The rules behind it are in the Switch spec (`spec/spec.md`) and wire format (`spec/wire-format.md`); the crate's design is in `docs/signer-design.md`.

## 1. What the signer does, and what the host supplies

The signer holds the identity key on behalf of the user. It enrolls the identity at a switch, approves apps and signs their certificates, keeps `identity.json` signed, delivered and published, renews, reduces and revokes apps, recovers from a lost provider, erases the account, and hands the identity to another signer. It signs only what it builds itself, and it commits every step to the host's store before it sends it, so a crash never makes it sign twice.

The host supplies, once per identity:

- **A key vault,** a `SecretVault`: the 32-byte identity secret in device-bound secure storage that isn't backed up, for example a platform keychain item of a this-device-only class, or a file wrapped by a hardware-backed key store and excluded from backups. `add` stores only into an empty vault, as one atomic step for every caller. The host opens it with `IdentityKeyring::create` (a new identity) or `IdentityKeyring::open`.
- **A `SignerEnv`:** the `store`; the `clock` requests are signed with; the `transport` to the switches; the identity's `homeserver`; and the `protocols` it supports.
- **A store** that gives every guarantee the `StateStore` trait of `pubky-switch-client` lists: a commit applies all of its writes or none, also across a crash; it is durable before it returns `Ok`; commits apply in order and a read sees every commit that returned before it; exclusive namespace acquisition and conditional commits exclude every competing writer, across processes; the store is excluded from device and cloud backups and encrypted at rest under a key kept like the app's keys; and a deletion removes the data from the store's files, not only from its index (for SQLite, `secure_delete`). The last one is what makes a hand-over's "deletes its records in every copy it keeps" true: a store that only unlinks the index leaves the handed-over records readable on the device. A backed-up store puts the records in copies the signer never deletes, and a restored device backup brings old records back behind the signer's mark.
- **A Homeserver session,** behind the `Homeserver` trait (`get`, `put`, `delete`), whose capabilities cover, for read and write, `/pub/pubky-switch/v1/` and `/priv/pubky-switch/v1/signer-backup.json`. A root session does. Request deadlines are the host's. The trait's contract is strict: `get` returns `None` only when there is no such file, and an error for anything else (a missing capability, a timeout, an error status); `put` returns `Ok` only once the Homeserver took the write, and `delete` only once the file is gone (also when there was none). A host that maps an error to `None` makes `Signer::restore_new` answer `Refusal::NoBackup` for a backup that is there, and the signer take a backup or an `identity.json` that is there as missing.
- **The protocols,** a `Protocols` set built with `Protocols::new` from every `Protocol` the host supports, each owning its scope names (for example the sample protocol `tasks` owning `tasks` and `tasks_sync`). A scope no registered protocol owns is refused in requests.
- **A schedule:** call `Signer::resume` after every `Signer::create` or `Signer::open`, and `Signer::run_due` at each start and on a schedule of the host's. A run is bounded in work and time, so it can be called often. When `RunDue::more_due()` is true, call `run_due` again soon, a minute later say, not at once.

**One `Signer` per identity, one call at a time.** Open one `Signer` per identity at a time, and never run two of its calls at once, for example from two threads through a binding's wrapper (the Rust methods take `&mut self`; a binding must keep that). The signer enforces the first through the store: every constructor acquires the identity's `signer/<identity>` namespace before it loads records or signs anything, and every commit is a conditional write (`commit_if`) under that ownership. A second instance, in another process (an app or push extension, a widget, a scheduled task) or as a second object in the same one, fails at its constructor with `SignerError::Store(StoreError::InUse)` and signs nothing: it gives up or tries again later, and never deletes or replaces records in answer (2.4). That holds only if the host's store implements the ownership contract of section 2.4 for every handle and process that shares it; a store that doesn't would let two instances each sign the next version from the same `signed_through` mark, two different documents at one version, which is the signer equivocating against itself. Work the host schedules, such as `Signer::run_due`, runs on the one open `Signer`. Dropping it doesn't always free the namespace at once: a canceled save keeps its lease until its worker finishes (2.4). To hand the store to another call, such as a key-only survey, `open` or `restore_over_unusable`, close the signer with `Signer::close`: it waits for such a save and returns with this signer holding nothing, though another owner, such as another process, can still take the namespace first (`StoreError::InUse`: try again later). After `StoreError::Unknown`, let the intended call read the records afresh from the store, since the write may already have taken effect.

The identity secret itself is the host's to back up for the user, for example as a seed phrase. The signer backs up its own records, without the key, on the Homeserver. Each alert carries the facts the host needs. The host chooses wording, controls and layout, including how to present alerts. Quoted messages are examples. `UserConfirmed::shown_and_confirmed()` is made by the host only after the user has seen the consequence of the call and confirmed it.

Types the signer takes or returns that come from the other crates of this repository: `IdentityDoc`, `AppCert`, `SignedDoc`, `ConnectRequests`, `AuthRequest` and `AppKeys` from `pubky-switch-core`, and the store, the clock, the transport and `ClientError` (inside `SignerError::Switch`) from `pubky-switch-client`.

## 2. The cases

Every error a call returns is a `SignerError`; a refusal a rule made is `SignerError::Refused` carrying a `Refusal`. "Alerts" are what `Signer::alerts()` returns until `Signer::clear_alert` removes them; "status" is `Signer::status()`. Read both after every call, whether it succeeded or failed.

### 2.1 First set-up and enrollment

| The case | How the host learns of it | What the user needs to know | What to do | What not to do |
|---|---|---|---|---|
| A new identity is set up | `IdentityKeyring::create(vault)` returns a keyring; `Signer::create(env, keyring, origin)` returns the signer; `Signer::status()` is `SignerStatus::Enrolling` | the chosen switch, "setting up" | call `Signer::resume`; on success the status is `SignerStatus::Signing` | do not show the identity as ready while `SignerStatus::Enrolling` |
| The enrollment couldn't be sent yet | `Signer::resume` returns `SignerError::Switch` or `SignerError::Homeserver`; status stays `SignerStatus::Enrolling` | "not reached yet, will retry" | call `resume` again later, or let `run_due` do it; split `SignerError::Switch` as 2.4 does | do not call `Signer::create` again: the flow is kept and resent unchanged, and `create` returns `Refusal::AlreadySetUp` |
| First discovery already found an account or its mark | `resume` returns `Refusal::FirstAccountPresent` and status is `SignerStatus::FirstAccountPresent`, including after reopening | the original service from `first_enrollment_origin`; this install signed no creation | offer the confirmed backup restore or the serving-account survey and confirmation in 2.13; if local state becomes unreadable, use the separate record-discard confirmation in 2.13; a surviving authenticated discovery can still locate the serving account for that survey; if the service has only a mark, offer the separate provider-loss survey | keep the signer records and the user's identity key |
| The original first creation expired | `resume` returns a verified `409 conflict` with `current.binding` equal to `expired`; the alert carries `FirstEnrollmentStop::Expired` | the original service address from `Signer::first_enrollment_origin` and that the earlier enrollment may have committed | after the user confirms, call `Signer::restart_first_enrollment(origin, UserConfirmed::shown_and_confirmed())`; an original receipt completes the held setup, otherwise a new creation requires the same absent service and store, no completed erasure and no identity document or backup | do not create a replacement from a timeout or a local clock reading |
| First enrollment cannot restart on that evidence | `Refusal::FirstEnrollmentUnavailable` | the install, service or identity history differs from a new identity's original setup | keep the records, check the selected origin and offer the applicable signer restore or confirmed provider-loss survey | never substitute another origin or assume the earlier request failed |
| The original creation meets an already serving account | The original key authenticates a request-bound `409 conflict` with `binding: changed`; the alert carries `FirstEnrollmentStop::Changed` | Show the account creation, the verified `identity_doc` and the recovery from `survey_first_enrollment_restore` at the original service. Explain that the earlier send may have committed and that this installation will take over the current history. | After the user confirms the survey, call `restore_first_enrollment` with it and the selected apps to drop if recovering without the backup. Use `resume` after an interruption. If the account changes after selecting key recovery, show a new `survey_key_recovery` and pass its confirmation to `restore`. | Keep the signed creation whenever the current account, original service or recovery evidence cannot be verified. |
| The service refuses the first request and it needs attention | The first call returns the authenticated `ClientError::Switch`. The saved `Alert::FirstEnrollmentHeld` carries `FirstEnrollmentStop::Refused` and the checked error code, or the binding reason above. | Show the code and original service. An earlier send may have committed. | After reopening, `SignerStatus::FirstEnrollmentHeld` and `Refusal::FirstEnrollmentHeld` tell the host to show the alert. Offer the applicable confirmed recovery, or clear the alert when the user chooses to retry the original step. | Do not clear alerts on a timer or infer the earlier send failed. |
| First discovery or creation has no verifiable answer | The saved alert carries `FirstEnrollmentStop::Unconfirmed`. A reply with no usable signature, a malformed answer or a refusal before the service read the body cannot establish the outcome. | Show the original service and explain that its answer could not be checked. | When the service can be checked again, clear the alert and call `resume` for the saved step. A lost connection or timeout alone remains retryable, as do temporary signed errors and early rate limits. | Do not treat an intermediary's status as the service's word or replace the signed creation. |
| The store already holds this identity | `Signer::create`, `Signer::restore_new` or `Signer::receive_hand_over` returns `Refusal::AlreadySetUp` | nothing new; open the existing signer | call `Signer::open` | do not delete the store's records to start over |
| The store holds no signer for this identity | `Signer::open` returns `Refusal::NotSetUp`; other calls before the first version return it too | the restore choice first: the vault already holds this identity's key, and the Homeserver may hold its signer backup | offer `Signer::restore_new` first; on `Refusal::NoBackup` (the Homeserver answered no such file, section 1), the survey of a recovery with the key alone (2.13); only when it answers `KeyRecoveryStop::NoCopy` and the user knows no service that serves the account (`Signer::survey_key_recovery_new_at`), `Signer::create`, which enrolls this same identity, the vault's key, as a first set-up: it makes no new identity and brings back no records, so it fits an identity whose set-up never finished | do not create a new identity over a vault that already holds one; do not offer `create` before the survey has answered `KeyRecoveryStop::NoCopy` |
| A switch origin that isn't valid | `Signer::create` returns `SignerError::InvalidData` | "not a valid switch address" | ask for another origin | do not retry the same origin |
| The Homeserver holds a signer backup this install can't open, before its first delivery | `Signer::resume` returns `Refusal::UnreadableBackup`, with `Alert::UnreadableBackupBeforeEnrollment` | that another install may already sign for this identity, or the backup is damaged; nothing is delivered | the user restores on the install that wrote it, or, sure that no other install signs, removes the backup from the Homeserver; then call `resume` | do not delete the backup on the user's behalf; do not clear the alert as a fix |

### 2.2 The key vault

| The case | How the host learns of it | What the user needs to know | What to do | What not to do |
|---|---|---|---|---|
| `add` stored the secret | the host's `SecretVault::add` returns `AddOutcome::Stored` | nothing | `load` must return it from then on, also after a crash | do not return `Stored` before the write is durable |
| `add` found a secret already there | the host's `add` returns `AddOutcome::Occupied`; the signer then returns `KeyError::Occupied` | "this device already holds an identity" | keep the held secret; open it with `IdentityKeyring::open` | do not overwrite, update, or delete-then-add the held secret |
| The vault can't be read or written, for example while the device is locked | `SignerError::Key` carrying `KeyError::Vault` | "unlock the device to go on" | retry once the device is unlocked | do not treat it as a missing key; do not offer a new identity |
| The vault holds no secret | `IdentityKeyring::open` returns `KeyError::Missing` | the set-up or restore choice, unless this install received a hand-over | when this install received a hand-over (`Signer::receive_hand_over` was called for the identity and didn't end in a refusal), call `Signer::resume_take_over(env, identity, keys, vault)` with the identity's public key and the `ReceivingApp::keys` it was given: the vault stays empty until the take-over wins; otherwise offer to create, or to restore with the key from the user's backup | do not create a new identity silently; do not offer the set-up choice over a take-over in progress |
| A hand-over from this install took effect | `Signer::open` (or any later call) returns `SignerError::HandedOver` with `install`, once it deleted the key and the records left; at the next start the vault holds no secret | that the identity is now with another install, and this one deleted its key | close the signer for this identity | do not offer a restore with the deleted key; do not treat it as a fault |
| The secret isn't this identity's | `KeyError::Mismatch` | "the key on this device isn't this identity's" | stop; ask the user which identity and key to use | do not sign with it or replace it automatically |
| The vault returned bytes that aren't 32 long | `IdentitySecret::from_slice` returns `KeyError::Malformed` | a fault of the vault | fix the vault code | do not pad or truncate the bytes |
| The secure random generator failed | `KeyError::Crypto` | a device fault | retry later | do not fall back to another random source |
| The secret leaves the vault | only for `ExportReason::HandOver`, inside `Signer::hand_over_to`; the host never receives it | the hand-over confirmation (2.12) | nothing beyond the hand-over | do not export the secret any other way; the signer's backup holds none |

### 2.3 Protocols

| The case | How the host learns of it | What the user needs to know | What to do | What not to do |
|---|---|---|---|---|
| No protocol registered | `Protocols::new` returns `ProtocolError::NoProtocols` | nothing to the user: a fault of the host's set-up | register at least one protocol | do not ship a build that fails here |
| A protocol name that isn't 1 to 32 of `a-z` and `0-9` starting with a letter | `ProtocolError::BadName` | as above | fix the protocol's name | do not rename it per device: every install must judge the same way |
| A protocol declares a scope outside its own root | `ProtocolError::ForeignRoot` | as above | declare only its name, or its name followed by `_` or `-` and more | do not claim another protocol's root |
| Two protocols under one name | `ProtocolError::DuplicateProtocol` | as above | register each once | do not register one protocol from two code paths |
| A protocol that owns no scope | `ProtocolError::NoScopes` | as above | give it at least one scope | do not register a protocol only for its name |
| A scope name that isn't a plain scope name | `ProtocolError::BadScopeName` | as above | declare roots without sub-scopes | do not declare `name:<sub>` forms |
| One scope declared twice | `ProtocolError::ScopeClaimedTwice` | as above | give each scope to one protocol | do not let two protocols share a scope |
| A protocol adds a grant path the Switch's rules don't allow | `ProtocolError::BadGrantPath`, at `Signer::review` or later inside `SignerError::Protocol` | as above | fix the protocol's `grant_paths` | do not add paths inside the Switch's own folders |
| A protocol answered with something malformed during a call | `SignerError::Protocol` | "this app version can't handle the request" | fix the protocol | do not retry the call unchanged |

### 2.4 The Homeserver and the store

| The case | How the host learns of it | What the user needs to know | What to do | What not to do |
|---|---|---|---|---|
| The Homeserver can't be read or written | `SignerError::Homeserver` | "can't reach your storage, will retry" | retry with `resume` or `run_due`; check the session's capabilities cover the backup path | do not drop the backup capability: without it every delivery stops |
| The host's store failed | `SignerError::Store` | a device storage fault | retry; the signer reads its records again after an unsure commit | do not edit the signer's namespace by hand |
| The signer's stored records cannot be read | `SignerError::Records` with `RecordsFault::Undecodable` (the position in `SignerRecord::State` or `SignerRecord::Flow`), `RecordsFault::InvalidHeader`, `RecordsFault::OtherIdentity`, `RecordsFault::Incomplete` (a flow without its state) or `RecordsFault::Damaged` (a stored account binding or first-enrollment origin is damaged) | that the identity is not lost, but this device cannot read its signer records | restart and retry once; if it persists, use the confirmed recovery below | do not treat a failed host read as corrupt signer records; do not edit or delete the namespace |
| A stored signed copy no longer verifies | `SignerError::StoredData`, from the state or flow, including `identity_doc`, `high_water`, `apps` and `approved` | that the device's kept signer data cannot be trusted | use the same confirmed recovery for a persistent local failure | do not report it as a bad network answer, or use an unreadable high-water mark as if no version had been delivered |
| The next records cannot be written as constructed | `SignerError::Records` with `RecordsFault::WriteRefused`, `RecordsFault::Encode` or `RecordsFault::Invariant` | that this app cannot complete the step | preserve the current records and report the fault; an invariant or refused write is not evidence of unreadable storage | do not discard healthy records or start recovery because of this error |
| Data the host supplied that the signer refuses | `SignerError::InvalidData` from a call's own input: an origin that isn't a switch origin (`Signer::create`, `Signer::declare_provider_loss`, `Signer::declare_provider_loss_confirming_records`), a record age of 0 (`Signer::set_record_max_age`), an expiry the certificate rules refuse (`Signer::renew`) | what is wrong with the input | ask the user for another value | do not retry the same input: it fails every time |
| Data from the network that doesn't verify | `SignerError::InvalidData` from data a switch, the Homeserver or a hand-over carried, such as a document that doesn't verify, or a revocation the switch took without a time | "the service sent data that doesn't check out" | retry later; if a signed answer keeps carrying it, consider a provider loss (2.9) | do not show the data as trusted |
| The switch can't be reached | `SignerError::Switch` carrying `ClientError::Transport` (`TransportError::Timeout`, `TransportError::Connect` and the others, except the two in the last row) | "can't reach the service, will retry" | `resume` and `run_due` resend the same bytes | do not build a new request in its place |
| An answer that doesn't verify or read | `SignerError::Switch` carrying `ClientError::BadServiceSignature` (its `status` unauthenticated), `ClientError::InvalidResponse`, `ClientError::Core` or `ClientError::Chain` | "the service's answer couldn't be checked"; nothing in it was used | as above; a signed head or transition proof that doesn't verify (`ClientError::Chain`) is evidence the service misbehaves: if it keeps coming, the user may declare a provider loss (2.9) | do not act on the status of an unverified answer: a `404` there isn't proof the account is gone (`Alert::AccountNotHosted`, 2.9) |
| A signed refusal | `SignerError::Switch` carrying `ClientError::Switch` with `code` and `retry_after`; `ClientError::retry()` says whether the same request may pass later | for `Some(Retry::No)`, that the service refused this step for good, with its code, and the step's own case above (for a renewal, `Alert::RenewalRefused`); for `429 rate_limited`, "busy, will retry"; otherwise "will retry" | on `429 rate_limited` (`Retry::AfterRetryAfter`), wait at least `retry_after` seconds before the next `resume` or `run_due`; for `Some(Retry::No)`, stop offering the same step and follow its case; otherwise leave it to `resume` and `run_due` | do not show "will retry" for a refusal for good; do not call again before `retry_after` |
| A call the client wouldn't send | `SignerError::Switch` carrying `ClientError::Usage` or `ClientError::Unpinned`, or `ClientError::Transport` with `TransportError::Refused` (the origin or an address it resolves to isn't one the client may connect to; nothing was sent) or `TransportError::InvalidRequest`: none passes on a retry | a fault of the host app | report it; fix the host's set-up | do not retry it in a loop |

A persistent local decoding or stored-copy failure can be recovered only on the user's confirmation. Show what unusable records may lose: undelivered approval claims, pending effects, changes not backed up, and local history. Obtain `RecordsDiscarded::shown_and_confirmed()` and call `Signer::restore_over_unusable(env, keyring, confirmed)`. This is a host attestation that the losses were shown, not verification of a UI interaction. The call acquires the namespace itself and diagnoses the current records; an earlier error is not permission to replace them. Close any old signer (`Signer::close`) and drop its credentials first. A live owner still yields `StoreError::InUse`. Usable records refuse with `AlreadySetUp`, and absent records with `NotSetUp`; use ordinary `restore` or `restore_new`, respectively. Store and vault errors, including a host's `StoreError::Corrupt`, never authorize replacement.

An enrolled signer with a signing alarm can lose the original account binding of its own high-water document. If no operation is pending, the confirmed restore can repair that binding when the private backup and the original account both verify the exact document. The same installation reopens with the alarm held. Show the alarm and let the holder acknowledge it through `clear_alert` (2.15) before signing again.

For first setup with a damaged stored origin, the holder can repair a pending signed creation on this installation. The original signed request must verify at the origin in the identity's private backup. The original service and store must serve the exact backed-up document at its recorded account creation. The repair retains the same install, request and alerts. Reopen the signer and show its pending first setup (2.1). With no signing alarm, the holder can choose the ordinary confirmed restore of the serving account. If a rollback or equivocation alarm survives and the install has no local high-water document, `clear_alert` returns that alarm. Keep showing it. The identity key holder can close the signer, survey a provider loss at their chosen replacement, and confirm the survey as described in 2.9. A missing or stale backup, or a missing signed creation, leaves the stored setup in place.

The call preserves restrictions from fully decoded current records for this identity. For an outstanding delivery of a signed successor, the signer can restore using the exact sealed backup that the flow retained and that the Homeserver holds. The open backup must name the same signed document, predecessor and original account. The signer asks that account whether it already holds the document or still needs the exact delivery. A missing or different backup leaves the flow in place. For a pending certificate renewal, a missing account binding on its preceding document can be repaired on the same install. The private backup must authenticate that document and the original account, and the same service must still hold it. The signed batch and identity documents must show which app certificate was replaced. The signer saves the binding with the original renewal and resumes its signed batches from the recorded position. If a batch itself is damaged, the confirmed backup restore retains the version and epoch of any signed successor it can verify. For an interrupted epoch completion, the same install can finish the signed identity delivery if every key batch was acknowledged and the original service confirms coverage for the listed certificates. The signed successor must preserve those certificates and permissions and complete exactly the epoch the signer already spent. An unanswered batch, missing coverage or a higher local floor keeps the operation pending. Other independently intact pending operations, erased accounts, hand-overs, take-overs and security alarms still hold. Verified local identity copies remain rollback marks even when another copy is damaged; known spent versions and key epochs, tombstones, pending revocations, earlier distrust times and owed cleanup survive replacement. Missing or invalid evidence is not proof of an empty history. A completed hand-over marker refuses with `NotNamed`; this call does not finish its key deletion or report `HandedOver`.

The backup, service and Homeserver checks of 2.13 complete before any replacement. When taking over from a backup, a fresh install ID and the complete verified candidate, including its exact initial flow and obligation to finish taking over, are committed atomically under the same owner. There is no delete-first step. After an unknown write or canceled call, reopen the actual stored pair: if replacement committed, another `restore_over_unusable` refuses the now usable records and `open` followed by `resume` finishes the durable obligation. A blocking write keeps ownership until its real completion. Cancellation cannot retract a remote request already sent; ordinary exact retries and reconciliation still apply.

Over damaged records, the key alone needs no separate store: `Signer::survey_provider_loss_with_key` and `Signer::declare_provider_loss_with_key` take whatever the store holds (2.9), and `RecordsDiscarded::and_key_recovery` recovers at the service (2.13). A separate empty store remains available through `restore_new`, with the damaged store set aside unused, when the user chooses recovery there. Open the identity key from the vault or its backup and follow 2.13. Both forms restore the backup's newest version, listed apps and certificates, removed and revoked App IDs, key bundle parts, settings and pending revocations it names, and add the switch's revoked or departed apps. A backed-up version not yet delivered goes first. Later runs find owed record deletions and raise their grant reminders again. A different empty store cannot preserve unreadable local-only facts: show that unbacked-up claims, unknown effects, unfinished changes and lost local history may not be recoverable. Never edit or delete a namespace and then call `open` or `create`. `restore_new` still fails on damaged records and refuses usable existing records with `AlreadySetUp`.

The local checks authenticate the stored signed artifacts that can be checked with the identity's public key. They do not authenticate every member of local state. In particular, a kept approval claim cannot be verified without its auth request's secret, which the signer does not keep. Opening a received hand-over also needs the correct caller app keys: a decryption failure with wrong keys is not by itself evidence of damaged records. Host store and vault failures retain their own errors.

The signer acquires `signer/<identity>` before loading records or signing anything. The store's required `acquire` returns a non-expiring `StoreLease`; its required `commit_if` checks the exact `StoreOwner` and applies the batch in one atomic operation. An unowned `commit` must refuse the entire batch if it touches any held namespace. `StoreError::InUse` means another owner is alive: retain that instance, or wait for all of its credentials and running store calls to finish and release ownership before opening another. `StoreError::NotOwner` makes the current handle inert; dispose of it and acquire afresh. Neither error permits deletion or replacement of the signer's records.

The host must implement real exclusion for every handle and process sharing the physical store. Ownership metadata is independent of replaceable signer values. An OS lock must use a stable resource that is never replaced along with a snapshot. A timeout or an expired heartbeat cannot authorize a second live owner. A process-local registry or a separate owner read followed by an unconditional write does not meet this contract. The generic Rust interface cannot certify that an arbitrary host implements these guarantees; `MemoryStore` gives process-local exclusion only and is not durable.

A canceled blocking save retains its lease until the worker actually finishes. The next call drains that worker and reloads state before taking another step. While this is unresolved, `approved` returns `StoreError::Unknown` instead of a claim. Dropping an instance does not retract a request already sent to a remote service: the next owner opens the exact durable flow and reconciles through `resume`. Cached status and high-water observations are not a substitute for that reconciliation.

### 2.5 Adding an app (approval)

| The case | How the host learns of it | What the user needs to know | What to do | What not to do |
|---|---|---|---|---|
| An app asks to be approved | the host receives an app request and its auth request; `Signer::review(request, auth)` returns an `AppReview` | the App ID, its scopes, its switch permissions, the keyed scopes, the purpose of each grant path and which paths the user can decline, and "renews" when `AppReview::renews` is true; for a request that renews, that a decline keeps the path out of this request's grant only, since a grant an earlier approval made still covers it until it expires or the app is revoked | let the user decline paths with `AppReview::decline`; before calling `Signer::approve`, persist in the host's device-bound store, until the claim is delivered, the original app and auth requests and `AppReview::consent()`, keyed by the request hash for this signer identity | do not grant `AppReview::asked_caps`: show it, never grant it; at a renewing request, do not tell the user a declined path was taken away |
| The scopes break the Switch's scope rule | `Refusal::Scopes` | the rule that failed, as its reason names it | turn the request down | do not approve a trimmed set the app didn't ask for |
| Scopes no registered protocol owns | `Refusal::UnknownScopes` | which scopes, and that this app version lacks support for them | turn the request down, or update the host app | do not register a placeholder protocol for them |
| A protocol's own rule refused the scopes or the paths left | `Refusal::ProtocolRule` | the protocol's name and reason | change the declines, or turn the request down | do not hide the protocol's reason |
| A decline of a path that can't be declined | `AppReview::decline` returns `Refusal::NotDeclinable` | that path stays granted | let the user decline only paths in `AppReview::grant_paths`; the set stays as it was | do not offer to exclude the app's record or backup paths |
| The request fails a check | `Refusal::AppRequest`, its reason naming the step | "this request isn't valid" | turn it down | do not retry the same request |
| The App ID was revoked or is being revoked | `Refusal::AppRequest` at `Signer::review`; `Refusal::CutOff` at a renewal | "this app was removed for good" | the app asks again with new keys, as a new app | do not approve the old App ID again |
| A stored counter is more than 2^20 ahead of its verified value | The signer ignores the scalar and continues from the verified value | No prompt | The next verified read or signature repairs the floor | Keep the signer records |
| A clock floor is too high for recovery without a copy | `Refusal::CounterClock` with `Counter::Version` or `Counter::Generation` | Correct the device clock | Repeat the provider-loss survey after correcting it | Keep the identity key |
| Pending signed bytes need a verified counter history | `Refusal::CounterCopyNeeded` with the affected counter | Waiting for a verified copy | Retry when the Homeserver, signer backup or switch copy is available | Keep the original bytes for retry |
| The next counter value exceeds the wire range | `Refusal::CounterExhausted` with `Counter::Version`, `Counter::Generation` or `Counter::Epoch` | The counter cannot advance by the required step | Advancing beyond the wire maximum requires a protocol change | Preserve the counter history |
| The device clock is off the switch's time | `Signer::approve` or `Signer::renew` returns `Refusal::ClockOff` with `device_ms` and `switch_ms` | that the device clock needs correcting; the two times are available for diagnostics | approve again once the clock is right | do not approve with the clock off |
| The approval is delivered and its claim released | `Signer::approve` returns an `ApprovedRequest`, or later `Signer::approved(&hash)` returns one, `hash` being the persisted `AppReview::request_hash()` | "approved" | deliver `ApprovedRequest::claim` to the auth request's relay, approve the Homeserver grant for exactly `ApprovedRequest::caps` with `approve_auth_with_capabilities`, then call `Signer::claim_delivered(&approved.request)` with its `ApprovedRequest::request`, the same 32 bytes | do not call `approve_auth` or grant the auth request's own capabilities |
| The approval's version is delivered but the claim is held | `Signer::approve` returns `Refusal::ClaimHeld`, naming the alarm's alert when still held | "approved, waiting for the service to be confirmed" | clear the alarm (2.15), then poll `Signer::approved(&hash)` with the persisted hash | do not send any claim or grant until `approved` returns one |
| The delivery didn't finish, or `approve` failed before it committed, or the host app restarted in between | `approve` returns a switch or Homeserver error, or the process ended; `approve` reads the switch before it commits, so an error there leaves no claim | "approval pending" | call `resume`, then `Signer::approved(&hash)`; deliver a returned claim as issued. If the successful resume leaves no claim, call `Signer::review` with the original requests, apply the saved choice with `ApprovalConsent::apply_to`, and pass that review to `Signer::approve` | do not ask the user for a new approval of the same request, unless `Refusal::ApprovalChanged`: then show the current review and obtain fresh consent before signing |
| A request that renews an app that hasn't joined | `approve` returns `Refusal::NotJoined` | "the app hasn't connected to the service yet" | the app joins first, then asks again | do not retry automatically |
| The newest version would be too large | `Refusal::IdentityTooLarge` with `SizedBody::Delivery` or `SizedBody::Enrollment` | the size and the cap | remove or purge apps (2.7) first | do not retry unchanged |

### 2.6 Renewal and reductions

| The case | How the host learns of it | What the user needs to know | What to do | What not to do |
|---|---|---|---|---|
| The user changes an app's scopes or expiry | `Signer::renew(app_id, CertChange)` returns the renewing version | the new scopes, permissions and expiry; that removing a scope with keys rotates the identity's keys | confirm the change with the user first | do not add a grant path here: that needs a new request from the app |
| The app isn't listed | `Refusal::NotListed` | "this app isn't connected" | refresh the app list | do not retry with the same App ID |
| The app hasn't joined | `Refusal::NotJoined` | "the app hasn't connected to the service yet" | wait for the app | do not retry in a loop |
| The App ID is revoked or departing | `Refusal::CutOff` | "this app was removed" | nothing | do not offer renew for an `AppStanding::Revoking` or `AppStanding::Removed` app |
| Another install's newer version was adopted meanwhile | `Refusal::Superseded` with the adopted version | "the identity changed elsewhere; try again" | show the refreshed app, let the user ask again | do not repeat the change automatically |
| The switch refused the renewal for good | the call's error, with `Alert::RenewalRefused` (`reduction`, `by_user`) | that the app keeps its listed certificate; for a reduction, that the access was NOT reduced | offer renew, reduce again, or revoke | do not show the reduction as done |
| A reduction's closing can't be delivered now | `Alert::ReductionNotClosed` naming the apps | that their earlier certificates aren't cut off yet | clear any signing alarm and call `resume` or `run_due` when the account is reachable | do not hide it: `clear_alert` keeps it until the closing is made |
| A certificate past half its lifetime isn't renewed by itself | `Alert::RenewalSkipped` with `RenewalSkip::UnownedScopes`, `RenewalSkip::PermissionsChanged` or `RenewalSkip::ScopesRefused` | which reason: scopes no protocol owns (for example `tasks` no longer registered), the permissions held and those it would get now, or the protocol and rule that refuse the scopes | the user renews it with the change shown, or removes it | do not renew it silently with other permissions |
| Two automatic renewals in a row no record took up | `Alert::RenewalsStopped` with `expires_at` | that the app lapses at that time unless renewed | offer renew or revoke | do not keep renewing it from the host |
| Such an app still owns open attempts | `Alert::LapsingWithOpenAttempts` with the count | the count and the expiry | offer renew, which keeps them its own | do not resolve the attempts for the user |
| The device clock is off the switch's time | `Alert::ClockOff`; `Refusal::ClockOff` on a user renewal | "set the device clock" | fix the clock; the alert clears itself at the next run | do not clear it and carry on |
| A rotation left an app without its new keys | `Alert::RotationSkipped` with the unowned scopes | which protocol support is missing | update the host app, or reduce the app to owned scopes | do not tell the user the app is up to date |
| A full-bundle request was refused by the switch | `Alert::FullBundleRefused` | the app may lack keys | the app asks again | do not resend from the host |

### 2.7 Revocation

| The case | How the host learns of it | What the user needs to know | What to do | What not to do |
|---|---|---|---|---|
| The user revokes an app | `Signer::open_attempts(app_id)` gives the count; `Signer::revoke(app_id, distrust_from, confirmed)` returns the version that removes it | the app; that it is cut off for good; the count of its open and `unknown` attempts (or "unknown" when the switch can't be reached); after a compromise, the earlier time from which its messages are distrusted | confirm, then revoke; once the revocation is kept, revoke its Homeserver grants at once (the row "The app is removed"): when `revoke` returned `Ok`, `Refusal::Recovering`, `SignerError::Alarm`, `Refusal::SwitchUnconfirmed`, or a switch or Homeserver error, and after any other error when `Signer::apps()` shows the app `AppStanding::Revoking` or `AppStanding::Removed`. `SignerError::NotNamed` and `Refusal::RecordsBehind` can come before the commit or after it, from the step that sends the revocation: after either, read `Signer::apps()`, and `AppStanding::Revoking` means the revocation is kept (revoke the grants; a restore in place sends it later), `AppStanding::Listed` that nothing was kept | do not let a failed `open_attempts` block the revocation; do not revoke the grants after a refusal that commits nothing (`Refusal::NotListed`, `Refusal::HandingOver`, `Refusal::TakingOver`, `Refusal::FlowInProgress`, `Refusal::NotSetUp`, `Refusal::Erased`): the app stays listed |
| The revocation is asked but no version removes the app yet | `Alert::RevocationPending` (`at_switch`); `Signer::apps()` shows `AppStanding::Revoking` | "being removed"; with `at_switch` true, "no longer served" | let `run_due` finish it | do not offer approve, renew or hand-over to it |
| The switch took the revocation but gave no time | `Alert::RevocationUnconfirmed` | "cut off at the service, not confirmed" | each run retries; if it keeps happening, consider another provider | do not show the app as removed yet |
| The revoked app owns open attempts | `Alert::RevokedWithOpenAttempts` with the count | the count, left for other apps or the user | nothing; it clears itself once it owns none | do not resolve the attempts for the user |
| The app is removed | `apps()` shows `AppStanding::Removed`; `Alert::GrantRevocationOwed` | "revoke its storage access" | revoke every Homeserver grant naming `/pub/pubky-switch/v1/apps/<app_id>.json`, then clear the alert | do not clear it before the grants are revoked; the signer revokes no grant itself |
| The app isn't listed | `Refusal::NotListed` | "this app isn't connected" | refresh | do not offer revoke for it again |
| A hand-over, take-over, erasure or recovery is in progress | `Refusal::HandingOver`, `Refusal::TakingOver`, `Refusal::FlowInProgress` (erasure), `Refusal::Recovering` (kept, with `Alert::RevocationPending`) | why it waits; during a recovery, that the revocation is kept for the new service, in this install's records only until the recovery completes: a new install restored from the recovery's backup doesn't have it (a restore in place keeps it) | for a hand-over, abort it first, then revoke; during a recovery, revoke the grants at once, and revoke the app again on any new install restored meanwhile | do not show it as done; do not revoke the grants on `Refusal::HandingOver`, `Refusal::TakingOver` or `Refusal::FlowInProgress`, which keep nothing |
| A removed app's entry is no longer needed | `Signer::purge_removed(app_id)` returns a version | nothing | purge once no more messages carrying its certificate are expected | do not purge an app not in `removed`: `Refusal::NotRemoved` |
| A device holding apps is lost | the user says so | the apps it held | revoke each from the signer, with `distrust_from` if it may be misused; revoke its grants at once once the revocation is kept (the first row); approve the replacement as a new app | do not re-approve a revoked App ID |

### 2.9 Provider loss and recovery

| The case | How the host learns of it | What the user needs to know | What to do | What not to do |
|---|---|---|---|---|
| The user declares the provider lost | `Signer::declare_provider_loss(origin, confirmed)` returns the new generation's version | the new service, and that apps rebuild their state there | confirm, then declare; it is allowed while an alarm is held, on an erased account, and during an erasure, which it ends | do not declare on a passing outage |
| Key-only provider loss | The vault holds the identity key | Apps rebuild at the chosen service | Follow the [procedure below](#provider-loss-with-the-identity-key) | A passing outage is insufficient |
| The recovery is not complete | `SignerStatus::Recovering` with `origin`; other calls return `Refusal::Recovering` | "moving to the new service" | `resume` preserves the current enrollment or delivery; revoke stays offered, kept for the new service with `Alert::RevocationPending` | do not offer other changes meanwhile |
| An enrollment cannot complete | an enrollment error with `SignerStatus::Recovering`; its original signed action remains pending | that an earlier send may have committed, even after expiry or loss of its receipt | resume the same action, or explicitly authorize a distinct recovery at this or another service; that authorization ends only the old enrollment continuation with its outcome still unknown | do not replace its intent automatically or reuse a late answer for the replacement |
| The recovery delivery was refused for good | `SignerStatus::RecoveryRefused` with `origin` | that this service refused the version | the user declares again, at that service or another | do not resend the refused version |
| The Homeserver's `identity.json` is missing or doesn't verify | `Refusal::HomeserverCopyMissing` or `Refusal::HomeserverCopyUnreadable` | that the user must confirm no other install signs | `Signer::declare_provider_loss_confirming_records(origin, confirmed)` | do not call it without that confirmation |
| An owed end of the staged admission failed | `Alert::AdmissionNotEnded` | that senders not yet admitted are still held at the new service | nothing: it stays owed and `run_due` sends it again; the alert goes once the switch shows the wait ended | do not call `Signer::end_staged_admission` for it |
| The end of the staged admission is left to the user | no alert or status names it: once the recovery's version is delivered (the status is no longer `SignerStatus::Recovering`), `Signer::apps()` lists an app whose `cert` grants the switch permission `lists.manage`, or whose `cert` is `None`, so the signer can't tell whether that app ends the wait | that senders not yet admitted may be held at the new service until that app, or the user, ends the wait | `Signer::end_staged_admission()` on the user's word, for example once the app that manages lists is gone for good; a call when no wait is staged sends nothing | do not call it while `Refusal::Recovering` or `Refusal::FlowInProgress` |
| Another flow is in progress | `Refusal::FlowInProgress` | "finishing a step first" | `resume`, then try again | do not start another step meanwhile |
| The service may not host the account | `Alert::AccountNotHosted` | that the service answered `404` with an answer its pinned key didn't sign, which an intermediary can send, or the service under a key it changed to, so nobody can confirm it; the account may have been erased from another copy of this install | wait: it clears itself at the next check that gets an answer the pinned key signs, an error included; a restore or a provider loss is the user's call on other evidence, never prompted by this alert alone | do not delete anything because of it; do not start a recovery or an enrollment elsewhere on it alone |
| The service says it holds no account | `Alert::ServiceHoldsNoAccount` | that the service answered, under its pinned key, that it holds no account for the identity: it lost the account, or it was erased from another copy of this install; nothing is signed while it answers so | offer a provider loss (`declare_provider_loss`, at this service or another) or a restore; it clears itself at the next answer the pinned key signs that shows an account, and once a recovery's version is delivered | do not delete anything because of it; do not declare the loss without the user's word |
| A declaration took a new key for a service | `Alert::ServiceKeyTaken` with `origin`, `pinned` and `service_key` | that the service at `origin` now signs with `service_key` in place of `pinned`, and that the recovery's version names it; the key is trusted on first use, as at a first enrollment | let the user check the new key with the operator by its own means, then clear the alert | do not hide it: a new key is the moment an on-path party could move the account onto a key of its own |

#### Provider loss with the identity key

1. **Check the key.** Match the opened keyring's `public_key()` to the identity. The holder can declare a loss with usable records in any state, with missing or unusable records, or after an at-service `Refusal::KeyRecovery`. Release the open signer and its store credentials.
2. **Survey the chosen service.** Call `Signer::survey_provider_loss_with_key(env, keyring, origin)`. Set a transport timeout. This read-only survey follows services named in signed copies.
3. **Show the survey.** Present these fields and let the user select additional apps to drop.
   - `origin`, `service_key` and the generation `lost` in `kind` (`KeyRecoveryKind::ProviderLoss`). `KeyRecoveryKind::AtService` belongs to section 2.13.
   - The highest signed copy's `generation`, `version` and `signer`. Other installs stop signing when delivery wins.
   - Each app in `apps`, its `AppFate` and any `distrust_from`. Explain `renewals_dropped`, `revoked`, `backup` and which apps need new keys.
4. **Declare only after confirmation.** Build `KeyRecoveryConfirmed::shown_and_confirmed(&survey, &dropped)` from **the survey shown**. Reopen the keyring for `Signer::declare_provider_loss_with_key(env, keyring, confirmed)`. Resume any committed enrollment or delivery. To declare again after building on a signed copy, the user can confirm another key-only declaration or use `Signer::declare_provider_loss`.

**Changed survey.** On `KeyRecoveryStop::SurveyChanged`, obtain, show and confirm a fresh survey. A newer or conflicting highest copy, new revocation, earlier distrust time or changed destination key or account invalidates confirmation. Previously confirmed evidence survives a source showing less. On `KeyRecoveryStop::NotServing` or switch errors across services, check the clock and offer another service.

**No signed copy.** When `lost` is `None` and `generation` and `version` are zero, show no prior signer. New values derive from time. Redeclare through this procedure only.

**Missing key after hand-over.** Unlock the original vault and call `Signer::resume_take_over` with the same receiving keys. After a recorded win, it installs the key before publication. Check the identity with `IdentityKeyring::open` even if publication fails. On `KeyError::Missing`, retain the sealed hand-over and receiving keys. If a win was recorded, retry local installation with `Signer::resume_take_over`. If the offer is still undecided, wait for the original service or recover with an independent copy of the identity key ([section 3.9](#39-hand-over--take-over), wire 3.12).

### 2.11 Erasure

| The case | How the host learns of it | What the user needs to know | What to do | What not to do |
|---|---|---|---|---|
| The user closes the account | `Signer::close_account(confirmed)` | that for the apps this is a provider loss and lookups fail closed; that `identity.json` and the app records leave the Homeserver; that each app's grant is the user's to revoke | confirm, then call; the erasure raises `Alert::GrantRevocationOwed` for each app still listed: revoke those grants once the status is `SignerStatus::Erased`, not before | do not erase without the confirmation; do not revoke a listed app's grants while the erasure can still be aborted or refused |
| The erasure is in progress | `SignerStatus::Erasing` | "closing the account" | `resume`; `Signer::abort_erasure()` ends it on the user's word; a provider loss declared meanwhile (2.9) ends it too | do not offer revocations meanwhile |

| The account is erased | `SignerStatus::Erased`; calls return `Refusal::Erased` | "account closed"; that a provider loss can bring the identity to a service again | show the app list read-only; revoke the grants each `Alert::GrantRevocationOwed` names; offer `Signer::declare_provider_loss` (2.9), which is allowed on an erased account | do not offer restore or revoke |

### 2.12 Hand-over to another signer install, and take-over

| The case | How the host learns of it | What the user needs to know | What to do | What not to do |
|---|---|---|---|---|
| The user hands the identity over | `Signer::hand_over_to(to_app, confirmed)`; status `SignerStatus::HandingOver` | the app taking over; that this install then stops and deletes its key; for a key derived from a wallet seed, that deletion can't make it unrecoverable | confirm, then call; tell the user to open the new app | do not offer other changes: they return `Refusal::HandingOver` |

| A revocation isn't delivered yet | `Refusal::RevocationOwed` | "finish removing the app first" | let `run_due` finish it | do not offer the hand-over until it is done |
| The target isn't current at the switch | `Refusal::TargetNotCurrent`; `Refusal::NotListed` for an app not listed | "that app can't take over now" | pick a current app | do not offer a revoked, expired or unlisted app |
| The switch refused to store the hand-over | `Alert::HandOverRefused` with `to_app` | the hand-over stays in progress | abort it unless that app takes over | do not show the hand-over as ended |
| The user calls it off | `Signer::abort_hand_over(confirmed)` returns `AbortOutcome::Aborted` with the version | "this device signs again" | nothing more | do not show the hand-over as in progress |
| The abort is sent but hasn't won yet | `abort_hand_over` returns `Refusal::HandingOver` | "calling off the hand-over" | `resume` or `run_due` sends it again; calling `abort_hand_over` again resends the same abort; it ends as `AbortOutcome::Aborted` or `AbortOutcome::SucceededBy` | do not show this device as signing again yet |
| The hand-over took effect first | `AbortOutcome::SucceededBy`, or `SignerError::HandedOver`, from any call | that the identity is now with another install, and this one deleted its key | close the signer for this identity | do not offer a restore with the deleted key |
| No hand-over to abort | `Refusal::NotHandingOver` | nothing | refresh | do not show an error to the user |
| Another install's version without its proof yet | `Refusal::SuccessorUnproven` with `install`, from `abort_hand_over`, `resume` or `run_due`, and `Alert::ManagedByOtherInstall` | "waiting for the new signer" | wait; if the new signer is lost, offer take-back | do not delete the key from the host |
| The new signer is lost | `Signer::take_back(confirmed)` returns a version, with `Alert::TakenBack` | that the new signer is taken to be lost; if it still runs it holds the key too | confirm, then call | do not offer it before `Refusal::SuccessorUnproven` shows; on `Refusal::NothingToTakeBack` hide it |
| The new app takes over | `Signer::receive_hand_over(env, app, vault)` on the new install; status `SignerStatus::TakingOver` | "taking over" | `resume`; after a restart, `Signer::resume_take_over(env, identity, keys, vault)` with the identity's public key and the same `ReceivingApp::keys`, since the vault stays empty until the take-over wins (2.2) | do not call it with a vault holding another identity: `KeyError::Occupied` |
| The hand-over isn't the switch's version | `Refusal::StaleHandOver` | "this hand-over is out of date" | nothing is kept; ask the old signer | do not retry the same hand-over |
| The take-over lost to an abort | `Refusal::TakeOverCancelled` | "the hand-over was called off" | nothing is kept | do not retry it |
| The switch refused the take-over's first delivery | `Alert::TakeOverRefused` | "taking over keeps failing" | the old signer aborts | do not delete what was received |
| The vault didn't take the received key | `Alert::KeyNotInstalled` | "finishing" | `resume` puts the key in again | do not clear the vault |
| No take-over in the store | `Refusal::NotTakingOver` | nothing | `Signer::open` | do not call `receive_hand_over` again on a set-up store |

### 2.13 Backup and restore

A backup carries the original account creation with its exact identity document. Restore and hand-over requests keep that target, including a first-document replay and a recovery already in progress. A signed conflict reporting a different creation does not authorize using the replacement account or prove that an earlier request failed. Keep the pending action and use the explicit recovery flow when the user authorizes a distinct action (account-binding Sections 1, 3 and 4).

| The case | How the host learns of it | What the user needs to know | What to do | What not to do |
|---|---|---|---|---|
| A new device of the same identity | `Signer::restore_new(env, keyring, confirmed)` with the key from the user's backup | whether the device the backup came from is still the user's; that the backup's records replace this install's | confirm, then call | do not use it while the old device still signs unless the user wants this one to take over |
| Records behind a newer own version | `SignerStatus::RecordsBehind`; `Alert::RecordsBehind` (`source`, `version`); `Refusal::RecordsBehind` | that this install's records are behind | `Signer::restore(confirmed)` | do not clear the alert as a fix: it stays until the restore |
| Another install signs | `SignerStatus::ManagedBy`; `Alert::ManagedByOtherInstall`; `SignerError::NotNamed` | which install signs; offer to take over here, showing that the other install then stops signing: once this one restores, it delivers a newer version naming itself, and the other finds it and signs no new version | `restore(confirmed)` on the user's word | do not sign from this install meanwhile; do not take over from an install the user still uses without saying so |
| No backup | `Refusal::NoBackup` | "no backup found" | check first that the host's `Homeserver::get` returned `None` only for no such file (section 1); the old device, if still the user's, makes a change so it writes one; otherwise the recovery with the key alone (below) | do not create a new identity over the same key; do not offer `create` as a restore |
| Unreadable backup | `Refusal::UnreadableBackup` | "backup can't be opened" | check the key is this identity's; then the recovery with the key alone (below) | do not delete the backup |
| Stale backup | `Refusal::StaleBackup` | "backup is out of date" | the recovery with the key alone (below), or a restore again once the newer version's backup is written | do not edit the backup or the store to get past it |
| The backup is missing, unreadable or stale | one of the three refusals above | the survey: `Signer::survey_key_recovery_new(env, keyring)` on a new device or over unusable records, or `Signer::survey_key_recovery_new_at(env, keyring, origin)` at a service the user gives (shown with `origin_supplied`), `Signer::survey_key_recovery()` in place (3.10) | the user confirms the survey, as shown, with any apps they drop: `KeyRecoveryConfirmed::shown_and_confirmed(&survey, &dropped)`, passed to `restore_new`, `restore`, or `RecordsDiscarded::and_key_recovery` for `restore_over_unusable` | do not build the confirmation from another survey than the one shown |
| Recovery with the key alone was interrupted before its version was signed | `Signer::pending_key_recovery` gives its original service | Offer to resume, or explain that stopping may retry the same existing enrollment to establish its result. The identity key stays in the vault. | To continue, call `Signer::resume`. If the holder confirms stopping, call `Signer::cancel_key_recovery` with `UserConfirmed::shown_and_confirmed()`. The original installation keeps its signing restrictions. A new store returns to the restore choice. | An unavailable or unverifiable enrollment reply keeps the operation pending. At `Refusal::NoPendingKeyRecovery` reopen or resume the current operation; a signed delivery keeps its original bytes. |
| The recovery with the key alone doesn't go ahead | `Refusal::KeyRecovery` with a `KeyRecoveryStop` | `KeyRecoveryStop::NoCopy`: no copy names a service; `KeyRecoveryStop::NotServing`: that service doesn't serve the account; `KeyRecoveryStop::SwitchCopy`: its copy names another origin or key, or doesn't verify; `KeyRecoveryStop::ServiceBehind`: a newer copy than the service's was seen; `KeyRecoveryStop::SurveyChanged`: the survey reads otherwise now; `KeyRecoveryStop::UnknownMembers`: the copy carries members this signer version doesn't read | `KeyRecoveryStop::SurveyChanged`: survey and confirm again. `KeyRecoveryStop::UnknownMembers`: update the app to a signer version that reads them. `KeyRecoveryStop::NoCopy`, or `KeyRecoveryStop::NotServing` (or a switch error) at a service the copy names that the user knows the account left: ask the user for the service that serves it and survey there with `Signer::survey_key_recovery_new_at`. A transport error in `SignerError::Switch` can also mean the current service is temporarily unreachable. Offer to retry there. The others: a provider loss declared with the key alone (2.9) | do not retry the same confirmation after `KeyRecoveryStop::SurveyChanged` |
| An enrollment answer named another service key during that recovery | `Alert::ServiceKeyNotFollowed` (`origin`, `kept`, `answered`) | both keys; the recovery kept the one the copy names | nothing | do not take the other key |
| The backup after the restore couldn't be written | `Alert::BackupNotWritten` | that the next change writes it; after a recovery with the key alone, that the next version, which removes the apps whose certificate wasn't found, writes it | nothing; `Signer::run_due` or any change makes that version | do not repeat the restore |
| A restore bounded a claimed epoch | `Alert::EpochFloorBounded` (`claimed`, `kept`) | a service or backup fault | nothing | do not repeat the restore |
| The backup didn't open or was missing, and was rewritten | `Alert::BackupUnreadable`, `Alert::BackupMissing` | the backup was rewritten | nothing | do not treat it as another install signing |
| The signer device itself is lost | the user says so | that revoking apps doesn't take the identity key back from whoever holds the lost device | `restore_new` on another device with the key from the user's backup; then revoke the lost device's apps | do not promise the key is safe |

### 2.14 Periodic work

| The case | How the host learns of it | What the user needs to know | What to do | What not to do |
|---|---|---|---|---|
| A run left work | `Signer::run_due` returns a `RunDue` whose `more_due()` is true | nothing | run again soon, a minute later say | do not call it in a tight loop |
| A run met an error | `Signer::run_due` returns an error | the recovery or refusal that needs attention | Handle the error and keep scheduling runs. During hand-over or take-over only `resume` runs. An early resume failure can stop other work. Routine step failures are reported after the remaining eligible steps. See the limits and error cases on `Signer::run_due`. | do not stop scheduling runs |
| A settings change | `Signer::set_record_max_age`, `Signer::set_connect_requests` return the version | the new setting | on `Refusal::FlowInProgress`, call `resume` first, then again | do not change settings during a hand-over, recovery or erasure |

### 2.15 Alarms

| The case | How the host learns of it | What the user needs to know | What to do | What not to do |
|---|---|---|---|---|
| A rollback | `Alert::Rollback` (`source`: `Source::Switch`, `Source::Homeserver` or `Source::Backup`), `SignerError::Alarm`, `SignerStatus::Alarm` | where it was seen, its version and the high-water version | the user clears it with `clear_alert`; the signer then delivers its newest version again | do not hide the alarm or work past it |
| An equivocation | `Alert::Equivocation` (`source`, `version`) | as above | as above | as above |
| A rollback where the switch held no copy at all (`version` is `None`) | `Alert::Rollback` with `Source::Switch` | that the service lost the account's state | clear it; the signer reads the switch's copy, and if none, raises it again: declare a provider loss (2.9) | do not expect a retry to fix it |
| Cleared, but the switch not confirmed yet | `Refusal::SwitchUnconfirmed` | "checking the service" | `resume`; if the alarm returns, consider a provider loss | do not clear the alert again in a loop |

## 3. Host integration checklist

After a call that changes state, read `Signer::status()` and `Signer::alerts()` again on success or failure. Use the current state for the actions offered to the user. Handle general failures as described in 2.4. A switch that can't be reached or an answer that can't be checked (`SignerError::Switch`), `SignerError::Homeserver`, `SignerError::Store`, `SignerError::Key` and `SignerError::InvalidData` from the network: show that the step will be retried, and leave the retry to `Signer::resume` or `Signer::run_due`, after `retry_after` on a `429`. A signed refusal for good, a `ClientError::Usage` or `ClientError::Unpinned`, and `SignerError::InvalidData` from the call's own input: never "will retry". `SignerError::Records` and `SignerError::StoredData`: follow the separate cases in 2.4; a refused write or invariant never authorizes discarding records.

### 3.1 Set-up

- [ ] Shows the choice: a new identity, or this identity from its key backup. When the vault already holds this identity's key (`Refusal::NotSetUp` at `Signer::open`), offers `Signer::restore_new` first, and `Signer::create` only after `Refusal::NoBackup` (2.1).
- [ ] New identity: calls `IdentityKeyring::create(vault)`; handles `KeyError::Occupied` (open the held identity instead with `IdentityKeyring::open`), `KeyError::Vault`, `KeyError::Crypto`, `KeyError::Missing` and `KeyError::Mismatch` (the vault lost the write).
- [ ] Asks for the switch origin, then calls `Signer::create(env, keyring, origin)`; handles `SignerError::InvalidData` (origin not valid) and `Refusal::AlreadySetUp` (call `Signer::open`).
- [ ] Calls `Signer::resume`; shows "setting up" while `SignerStatus::Enrolling`, done at `SignerStatus::Signing`; an enrollment the switch keeps refusing is shown as refused, with its unconfirmed status, not as "will retry" (2.1).
- [ ] Handles `Refusal::UnreadableBackup` with `Alert::UnreadableBackupBeforeEnrollment`: shows that another install may sign for this identity, and offers the restore on that install, or the removal of the backup by the user.
- [ ] Asks the user to back up the identity key itself, and says the signer's backup on the Homeserver doesn't hold it.
- [ ] At every later start: `IdentityKeyring::open`; on `KeyError::Missing` when this install received a hand-over, `Signer::resume_take_over(env, identity, keys, vault)` (3.9) in place of the next two steps, and the set-up choice otherwise; `Signer::open` (handles `Refusal::NotSetUp`; `SignerError::Records` or `SignerError::StoredData` as 2.4 says, distinguishing persistent local read failures from a refused write or invariant; and `SignerError::HandedOver`: a hand-over from this install took effect and its key and records are deleted, so it shows that the identity is with another install and stops offering signer actions for it); `Signer::resume`; `Signer::run_due`.
- [ ] Confirmed by the user: nothing beyond the choice and the origin.

### 3.2 Approve an app

The [Rust signer example](../crates/pubky-switch-signer/examples/approve_app.rs) takes an open signer and resumes saved approvals after restart. The host supplies device-bound storage, confirmation, relay delivery and the Homeserver grant. Build it with `cargo build -p pubky-switch-signer --example approve_app`.

- [ ] Calls `Signer::review(request, auth)` and shows the `AppReview`: the App ID, the scopes, the switch permissions, the scopes with keys, the purpose of each grant path and which paths the user can decline, and "renews this app" when `AppReview::renews` is true; for a renewing request, says that a decline keeps the path out of this request's grant only, and that an earlier approval's grant still covers it until it expires or the app is revoked.
- [ ] Shows the rights of each peer permission separately (Switch spec 3.2, 7, 12.6).
  - `lists.read` reads peer admission, deny entries, flags, live invite registrations and pending connect requests. After provider loss it can contribute saved deny entries.
  - `lists.manage` adds or removes kept peers, removes reply grants and manages deny entries. Adding a kept peer answers that peer's pending connect request. Adding a deny entry removes the pending request. After provider loss it can restore kept peers and deny entries.
  - `reply.add` grants reply access and manages invite codes. A reply grant answers a pending connect request. A direct decline also requires `reply.add`. After provider loss it can grant reply access again to eligible peers from the app's own records.
- [ ] Shows `AppReview::asked_caps` for information only.
- [ ] Handles at `Signer::review`: `Refusal::Scopes`, `Refusal::UnknownScopes` (name the missing protocol support), `Refusal::ProtocolRule`, `Refusal::AppRequest`, `Refusal::NotSetUp`, `SignerError::Protocol`.
- [ ] When the user changes their selection, calls `AppReview::decline(paths)`. If it returns `Refusal::NotDeclinable` or `Refusal::ProtocolRule`, keeps the previous selection.
- [ ] Confirmed by the user: the approval, with the declines shown.
- [ ] Before calling `Signer::approve`, persists until the claim is delivered, in the host's device-bound store and never in logs: the original app and auth requests and `AppReview::consent()`, keyed by request hash for this signer identity. Then calls `Signer::approve` with the `AppReview`; handles `Refusal::ApprovalChanged` (show a fresh review; the saved choice is retired), `Refusal::ClockOff` (ask the user to correct the clock), `Refusal::ClaimHeld` (wait for the alarm, 3.11), `Refusal::NotJoined`, `Refusal::CutOff`, `Refusal::IdentityTooLarge`, `Refusal::FlowInProgress`, `Refusal::Recovering`, `Refusal::HandingOver`, `Refusal::TakingOver`, `Refusal::SwitchUnconfirmed`, `Refusal::Erased`, `Refusal::RecordsBehind`, `SignerError::NotNamed`, `SignerError::Alarm`.
- [ ] After a switch or Homeserver error from `approve`, and at the next start with a confirmed approval whose grant is still pending: calls `Signer::resume`, then `Signer::approved(&hash)` with the persisted hash; delivers a returned claim with its original capabilities. When a successful resume leaves no claim, applies the saved `ApprovalConsent` to a fresh `Signer::review` and calls `Signer::approve`. On `Refusal::ApprovalChanged` at either step, retires the uncommitted choice and asks the user to confirm the current review; otherwise it never asks the user for a new approval of the same request. A refusal from `Signer::review` here also ends the saved approval.
- [ ] With the `ApprovedRequest` (from `approve`, or later from `Signer::approved(&hash)`): delivers `ApprovedRequest::claim` to the auth request's relay, approves the Homeserver grant for exactly `ApprovedRequest::caps` with `approve_auth_with_capabilities`, then durably marks the grant complete in the same host record before calling `Signer::claim_delivered(&approved.request)`, `ApprovedRequest::request` being the same 32 bytes as `AppReview::request_hash()`.
- [ ] Removes the saved record after `claim_delivered` succeeds. After a restart with the grant marked complete, calls `claim_delivered` again and removes the record. An already cleared claim succeeds, so this step requires neither another approval nor another delivery.
- [ ] Never grants with `approve_auth`, never `AppReview::asked_caps`, never before a claim is returned.

### 3.3 App list and app detail

- [ ] Calls `Signer::apps()` and lists each `AppSummary` with its current standing.
- [ ] Shows the standing: `AppStanding::Listed`, `AppStanding::Revoking` (with "no longer served" when `at_switch` is true), `AppStanding::Removed`.
- [ ] Detail: the certificate's scopes, switch permissions, `issued_at` and `expires_at`; whether a renewal is open; the protocols that own its scopes and any scope none owns; `distrust_from`; the automatic renewals no record took up; the alerts that name it (`AppSummary::alerts`).
- [ ] For a listed app whose `cert` is `None` (a version adopted from another install), shows its scopes as unknown here.
- [ ] Offers renew, reduce and revoke on a listed app only; offers `Signer::purge_removed` on a removed one; handles `Refusal::NotRemoved`.
- [ ] Read-only while the status isn't `SignerStatus::Signing`, but for revoke on a listed app, which stays offered at `SignerStatus::Alarm` (the app is revoked at the switch, its version waits for the alarm) and at `SignerStatus::Recovering` (kept for the new service with `Alert::RevocationPending`).
- [ ] Viewing app details requires no confirmation. Each action below has its own confirmation rules.

### 3.4 Renew / reduce

- [ ] Shows the current terms and the new ones: scopes, switch permissions (from `Protocols::terms`), expiry; says that removing a scope with keys rotates the identity's keys, and that removing a scope no protocol owns rotates too.
- [ ] Confirmed by the user: the change.
- [ ] Calls `Signer::renew(app_id, CertChange)`; handles `Refusal::NotListed`, `Refusal::NotJoined`, `Refusal::CutOff`, `Refusal::Superseded` (show the refreshed app), `Refusal::ClockOff`, `Refusal::UnknownScopes`, `Refusal::Scopes`, `Refusal::ProtocolRule`, `Refusal::IdentityTooLarge`, `Refusal::FlowInProgress`, `SignerError::InvalidData` (expiry refused).
- [ ] On a refusal by the switch, shows `Alert::RenewalRefused`, and for a reduction that the access was not reduced.
- [ ] After a reduction, shows `Alert::ReductionNotClosed` while the earlier certificate isn't cut off yet.
- [ ] Offers renew from `Alert::RenewalsStopped`, `Alert::RenewalSkipped` and `Alert::LapsingWithOpenAttempts`.

### 3.5 Revoke

- [ ] Calls `Signer::open_attempts(app_id)`; shows the count, or "unknown" when the call fails.
- [ ] Shows that the app is cut off for good, and asks whether it may have been used against the user; if so, asks the earlier time from which its messages are distrusted.
- [ ] Confirmed by the user: the revocation, with the count and the time shown.
- [ ] Calls `Signer::revoke(app_id, distrust_from, UserConfirmed::shown_and_confirmed())`; handles `Refusal::NotListed`, `Refusal::HandingOver` (abort first), `Refusal::TakingOver`, `Refusal::FlowInProgress` (an erasure), `Refusal::NotSetUp`, `SignerError::NotNamed`, `Refusal::RecordsBehind`, `Refusal::Erased`, `Refusal::Recovering` (kept, shown pending), `SignerError::Alarm` (revoked at the switch, the version waits), `Refusal::SwitchUnconfirmed` (kept, the version waits).
- [ ] Revokes every Homeserver grant naming the app's record path at once, or asks the user to, only once the revocation is kept: `revoke` returned `Ok`, `Refusal::Recovering`, `SignerError::Alarm`, `Refusal::SwitchUnconfirmed`, or a switch or Homeserver error; after any other error, only when `Signer::apps()` shows the app `AppStanding::Revoking` or `AppStanding::Removed`. After `SignerError::NotNamed` or `Refusal::RecordsBehind`, which can come before the revocation is kept or after it, it reads `Signer::apps()`: `AppStanding::Revoking` means kept, so the grants go; `AppStanding::Listed` means nothing was kept. After `Refusal::NotListed`, `Refusal::HandingOver`, `Refusal::TakingOver`, `Refusal::FlowInProgress`, `Refusal::NotSetUp` or `Refusal::Erased` nothing is committed, the app stays listed, and the grants stay.
- [ ] Shows `Alert::RevocationPending`, `Alert::RevocationUnconfirmed`, `Alert::RevokedWithOpenAttempts`, and clears `Alert::GrantRevocationOwed` once the grants are revoked.

### 3.6 Recover from a provider loss

For a declaration with the identity key alone, follow [the survey and confirmation procedure](#provider-loss-with-the-identity-key). For a declaration from an open signer, use the checklist below.

- [ ] Asks the new service's origin.
- [ ] Shows the new service and that apps rebuild their state there.
- [ ] Confirmed by the user: the declaration.
- [ ] Calls `Signer::declare_provider_loss(origin, confirmed)`; handles `Refusal::HomeserverCopyMissing` and `Refusal::HomeserverCopyUnreadable` by asking the user to confirm also that no other install signs, then calls `Signer::declare_provider_loss_confirming_records(origin, confirmed)`.
- [ ] Handles `Refusal::NotSetUp`, `SignerError::NotNamed`, `Refusal::RecordsBehind`, `Refusal::HandingOver`, `Refusal::TakingOver`, `Refusal::FlowInProgress`, `Refusal::IdentityTooLarge`, `SignerError::InvalidData` (origin not valid).
- [ ] Shows `SignerStatus::Recovering` while the version waits, and `SignerStatus::RecoveryRefused` with the option to declare again.
- [ ] Once the recovery's version is delivered, while `Signer::apps()` lists an app whose `cert` grants `lists.manage` or whose `cert` is `None` (the wait the signer leaves to the user, 2.9), offers `Signer::end_staged_admission()` for when the user says the waiting senders may come in; handles `Refusal::Recovering` and `Refusal::FlowInProgress`.
- [ ] Shows `Alert::AdmissionNotEnded` with no action: `run_due` sends the owed end again.

### 3.7 Move

- [ ] Says that this signer has no cooperative move, and offers the provider-loss flow in 3.6 for the new provider.
- [ ] Shows `Alert::IdentityNearLimit` and `Refusal::IdentityTooLarge` with `SizedBody::Enrollment`, and offers to remove or purge apps first.

### 3.8 Erase the account

- [ ] Shows that for the apps this is a provider loss and lookups of the identity fail closed; that `identity.json` and the app records leave the Homeserver; that each app's grant is the user's to revoke.
- [ ] Confirmed by the user: the erasure.
- [ ] Calls `Signer::close_account(confirmed)`; handles `Refusal::Erased`, `Refusal::ErasureRefused`, `Refusal::FlowInProgress`, `Refusal::HandingOver`, `Refusal::TakingOver`, `Refusal::Recovering`, `Refusal::RecordsBehind`, `Refusal::SwitchUnconfirmed`, `SignerError::NotNamed`, `SignerError::Alarm`.
- [ ] Shows `SignerStatus::Erasing`, `SignerStatus::ErasedUnconfirmed` and `SignerStatus::Erased`. For `SignerStatus::ErasedUnconfirmed` it shows "looks closed, not confirmed yet" and no definite time: the first run at least 24 hours after `since_ms` (device clock) that still meets the switch's unsigned `404` confirms it, and an answer the pinned service key signs meanwhile ends the wait, the status going back to `SignerStatus::Erasing`.
- [ ] Lists each `Alert::GrantRevocationOwed`; for an app the erasure found still listed, revokes the grant only once the status is `SignerStatus::Erased` (an aborted or refused erasure withdraws those alerts); clears each alert once its grant is revoked.
- [ ] Offers `Signer::abort_erasure()` while `SignerStatus::Erasing`; handles `Refusal::ErasureUnanswered` and `Refusal::NotErasing`.
- [ ] At `SignerStatus::Erased`, and during an erasure, offers a provider loss (3.6): `Signer::declare_provider_loss` is allowed on an erased account and ends an erasure in progress.

### 3.9 Hand over / take over

- [ ] Old signer: lists the current apps that can take over; shows the app taking over and that this install then stops and deletes its key (and, for a key derived from a wallet seed, that the deletion can't make it unrecoverable).
- [ ] Confirmed by the user: the hand-over.
- [ ] Calls `Signer::hand_over_to(to_app, confirmed)`; handles `Refusal::ClosingOwed` (2.12: retry the owed closing after the account can be verified), `Refusal::RevocationOwed`, `Refusal::NotListed`, `Refusal::TargetNotCurrent`, `Refusal::FlowInProgress` (call `resume` first), `Refusal::Recovering`, `Refusal::RecordsBehind`, `Refusal::Erased`, `Refusal::HandingOver` (a hand-over is in progress already), `Refusal::TakingOver`, `Refusal::SwitchUnconfirmed`, `SignerError::NotNamed`, `SignerError::Alarm`.
- [ ] Shows `SignerStatus::HandingOver` and `Alert::HandOverRefused`; tells the user to open the new app.
- [ ] Offers abort, confirmed by the user: `Signer::abort_hand_over(confirmed)`; handles `AbortOutcome::Aborted`, `AbortOutcome::SucceededBy`, `Refusal::HandingOver` (the abort is sent but hasn't won yet: shown as calling off, sent again by `resume` and `run_due`), `Refusal::SuccessorUnproven`, `Refusal::NotHandingOver`.
- [ ] On `Refusal::SuccessorUnproven`, from `abort_hand_over`, `resume` or `run_due`, offers take-back, confirmed by the user that the new signer is lost: `Signer::take_back(confirmed)`; handles `Refusal::NothingToTakeBack`, `SignerError::HandedOver`, and shows `Alert::TakenBack`.
- [ ] On `SignerError::HandedOver` from any call: shows that the identity is with another install now, and stops offering signer actions for it.
- [ ] New signer: calls `Signer::receive_hand_over(env, app, vault)` with an empty vault; shows `SignerStatus::TakingOver`; handles `Refusal::AlreadySetUp`, `KeyError::Occupied`, `SignerError::InvalidData`, `Refusal::StaleHandOver`, `Refusal::TakeOverCancelled`; keeps the identity's public key and the `ReceivingApp::keys`; after a restart, with the vault still empty until the take-over wins, calls `Signer::resume_take_over(env, identity, keys, vault)` and handles `Refusal::NotTakingOver` and `Refusal::NotSetUp`; shows `Alert::TakeOverRefused` and `Alert::KeyNotInstalled`.
- [ ] If the old service disappears after the receiving install recorded that its delivery won, unlock its original vault and call `Signer::resume_take_over` with the same receiving app keys. It installs the key and reads it back before trying to publish. Even if publication then reports a connection error, open that vault with `IdentityKeyring::open` and check its public identity. With the received identity's installed key, show the result of `Signer::survey_provider_loss_with_key` for the user's chosen replacement, obtain the user's confirmation, and call `Signer::declare_provider_loss_with_key`. If the vault still reports `KeyError::Missing`, keep the saved hand-over and its receiving app keys. A pending offer without a verified win still needs its original service to decide it, or the user can recover with a separate copy of the identity key.

### 3.10 Restore

- [ ] Shows whether the device the backup came from is still the user's, and that the backup's records replace this install's.
- [ ] Confirmed by the user: the restore.
- [ ] On a new device, or after a persistent local read or stored-copy failure (2.4), into a new, empty store (for example a fresh database file), with the damaged store set aside unused, never its namespace deleted or edited and then `open` or `create` called on it: `IdentityKeyring::open` on this device's vault, or on a new device's vault that holds the backed-up secret, then `Signer::restore_new(env, keyring, confirmed)`; shows what the user redoes afterwards, and that claims and revocations not delivered yet are lost, as 2.4 lists.
- [ ] In place, offered at `SignerStatus::RecordsBehind` or `SignerStatus::ManagedBy`: `Signer::restore(confirmed)`; at `SignerStatus::ManagedBy`, shows first that the other install stops signing once this one restores.
- [ ] Handles `Refusal::NoBackup` (after checking the Homeserver answered no such file; no restore, and `Signer::create` is no substitute), `Refusal::UnreadableBackup`, `Refusal::StaleBackup`, `Refusal::Erased`, `Refusal::FlowInProgress`, `Refusal::HandingOver`, `Refusal::TakingOver`, `Refusal::AlreadySetUp`.
- [ ] Shows `Alert::BackupNotWritten` and `Alert::EpochFloorBounded` when raised.
- [ ] At `Refusal::NoBackup`, `Refusal::UnreadableBackup` or `Refusal::StaleBackup`, offers the recovery with the key alone: shows the survey (`KeyRecoverySurvey`): the service (`origin`), and, with `origin_supplied`, that it is the one the user gave, the version it builds on and its `generation`, the install that version names (`signer`), which stops signing, and every other install with it; each listed app with its `AppFate`: `AppFate::Stays` with a choice to drop it, `AppFate::RemovedAtSwitch` with its `distrust_from`, `AppFate::RevocationPending` with its `distrust_from`, `AppFate::CertificateNotFound` (revoked, approved again under a new key); `renewals_dropped`; how many App IDs stay `revoked`; the `backup` found: `BackupFound::Missing`, `BackupFound::Unreadable`, `BackupFound::Stale` (its certificates and revoked App IDs still count), or `BackupFound::Matches` (the restore takes it, losing nothing); and what a recovery loses (spec 12.8). Confirmed by the user, calls the restore again with `KeyRecoveryConfirmed::shown_and_confirmed(&survey, &dropped)`.
- [ ] Handles `Refusal::KeyRecovery` with each `KeyRecoveryStop`, as 2.13 lists, and shows `Alert::ServiceKeyNotFollowed`.

### 3.11 Alerts

- [ ] Makes each alert from `Signer::alerts()` available with its facts.
- [ ] On dismissal calls `Signer::clear_alert(alert)`; for `Alert::Rollback` and `Alert::Equivocation`, handles the alarm coming back (`SignerError::Alarm`) and `Refusal::SwitchUnconfirmed`.
- [ ] Keeps showing `Alert::ReductionNotClosed` and `Alert::RecordsBehind` after a dismissal, since the signer keeps them until their cause is gone.
- [ ] For `Alert::GrantRevocationOwed`, dismisses only after the grants are revoked.
- [ ] Never dismisses an alert the user hasn't seen.

### 3.12 Signer status

- [ ] Reads `Signer::status()` after every call and uses it to decide what the user can do: `SignerStatus::Enrolling`, `SignerStatus::Signing`, `SignerStatus::ManagedBy` (offer restore), `SignerStatus::RecordsBehind` (offer restore), `SignerStatus::HandingOver` (offer abort), `SignerStatus::TakingOver`, `SignerStatus::Alarm` (show the active alarm), `SignerStatus::Erasing` (offer abort), `SignerStatus::ErasedUnconfirmed`, `SignerStatus::Erased`, `SignerStatus::Recovering`, `SignerStatus::RecoveryRefused` (offer to declare again).
- [ ] At `SignerStatus::FirstEnrollmentHeld`, shows the original service and the reason in `Alert::FirstEnrollmentHeld`. Offers the retry or confirmed recovery for that reason in 2.1.
- [ ] At `SignerStatus::FirstAccountPresent`, shows the original service and explains that this installation signed no creation. Offers confirmed backup restore or a serving-account survey. If only the service's mark remains, offers the provider-loss survey (2.1 and 2.13).
- [ ] Turns the app list read-only whenever the status isn't `SignerStatus::Signing`, but for revoke, which stays offered at `SignerStatus::Alarm` and `SignerStatus::Recovering` (3.3).
